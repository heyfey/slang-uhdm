=============================================================================
(2) SURELOG — WHY A CLASS TYPEDEF FILES A LATE BINDING AND A STRUCT DOES NOT
=============================================================================

§ classScopedTdImportCopyLocalUnsupported198's three sites, unchanged, with the
FIRST one reached for a different reason:

1. THE HOME BODY DEGRADES FIRST.  `CompileHelper::compileDatastructureTypespec`
   walks the DataType chain (CompileType.cpp:852-861): a TypeDef contributes
   `parent_tpd->getTypespec()` and BREAKS only if that typespec already exists.
   A struct / enum / union / SimpleType typedef has one by then
   (CompileType.cpp:860-897, `st->getTypespec()` / `en->getTypespec()` /
   `sit->getTypespec()`); a typedef whose target is a CLASS does not, and the
   walk has to reach the ClassDefinition arm (CompileType.cpp:902-905) to build
   a `class_typespec`.  When it cannot, `result` stays null and the named-type
   arm mints the placeholder — CompileType.cpp:1617-1626,
   `unsupported_typespec` with `VpiName(typeName)` (the WRITTEN name) and
   `populateCoreMembers(type, type, ref)` (the WRITTEN TYPE TOKEN's span).
   That is golden's object, field for field: name `uvm_reg_field_cb_iter`, span
   1128:10-1128:31.
2. THE DECLARATION IS FILED FOR LATE REPAIR.  `compileVariable`'s final arm
   registers it — CompileType.cpp:421-431,
   `if (ts->UhdmType() == uhdmunsupported_typespec)
      component->needLateTypedefBinding(ref);` — and the block-item form does
   the same at CompileStmt.cpp:1799-1806.  That is why golden's variable is a
   `ref_var` in the HOME as well as in the clone (arm A, every class cell).
3. THE IMPORTER COPIES AT COLLECT TIME.
   `CompilePackage::collectObjects_`'s `CollectType::FUNCTION` pass calls
   `m_helper.importPackage(...)` (CompilePackage.cpp:141-151), and
   `CompileHelper::importPackage` deep-copies each imported task_func with
   `UHDM::clone_tree` WHEN THE IMPORTER IS A PACKAGE (CompileHelper.cpp:299-324).
   The copy carries a COPY of the placeholder, `vpiInstance` (the HOME package)
   included.
4. THE REPAIR IS POINTER-KEYED AND CANNOT REACH THE COPY.
   `ElaborationStep::bindTypedefs_` walks `comp->getLateTypedefBinding()` and
   records `getSwapedObjects().emplace(orig_ut, tps)` keyed on the ORIGINAL
   placeholder OBJECT (ElaborationStep.cpp:302-321), and
   `swapTypespecPointersInUhdm` then rewrites every `expr`'s `Typespec` in the
   serializer.  The clone's `ref_typespec` points at its own copied object,
   which is not a key in that map: the home is repaired, the clone is not.

WHICH TYPEDEF KINDS FILE LATE BINDINGS, MEASURED RATHER THAN READ OFF THE
SOURCE (arm A, both views, both sites): specialisation YES, plain class handle
YES, struct NO, enum NO, packed vector NO, int NO.  A class handle written
WITHOUT a typedef (arm B `bNoTd202b` / `kNoTd202b`) is NOT degraded either —
golden keeps an UNNAMED `class_typespec` with no instance, in the clone as in
the home, and so do we, on both binaries.

UNLIKE § 198, THE ELAB VIEW DOES NOT UNDO IT.  § impCloneDeclRangeNoBind200's
law is inert under `-elabuhdm` because `ElaboratorListener::leaveRef_obj`
re-binds dangling `ref_obj`s.  Nothing re-resolves a `ref_typespec`'s
`Actual_typespec`, so this law's cells read the same in both views — arm A, C
and E all score identically in def and elab.
