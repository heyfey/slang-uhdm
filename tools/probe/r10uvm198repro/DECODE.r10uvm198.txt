B. SURELOG — WHY THE CLONE KEEPS A PLACEHOLDER THE HOME DOES NOT
   The question was whether the importer RE-COMPILES the cloned body in its own
   scope (§ 36's "window") or COPIES a home object.  It copies, and three sites
   say so:

   1. CompileType.cpp:421-431 — compileVariable's final arm mints a `ref_var`
      and, when compileTypespec answered an unsupported_typespec, registers the
      declaration for late repair: `component->needLateTypedefBinding(ref)`.
      CompileStmt.cpp:1799-1806 does the same for the block-item form.  A
      class-scope typedef is not in the PACKAGE's data-type map and an
      out-of-body method is a PACKAGE item, so the HOME's own copy takes this arm
      — which is exactly why golden's variable is a `ref_var` in the HOME as well
      as in the clone (grid arm A, every cell, both views).
   2. CompilePackage.cpp:141-151 and :167-170 — the importing package's
      CollectType::FUNCTION pass calls CompileHelper::importPackage, and
      CompileHelper.cpp:299-324 deep-copies every imported task_func with
      UHDM::clone_tree when the importer is a package.  This happens in the
      COMPILE step, i.e. BEFORE elaboration: the copy carries a COPY of the
      placeholder, vpiInstance (the HOME package) included.
   3. ElaborationStep.cpp:303-321 (and :334-408) — bindTypedefs_ walks
      `comp->getLateTypedefBinding()` and records
      `getSwapedObjects().emplace(orig_ut, tps)`, keyed on the ORIGINAL
      placeholder POINTER; :415 then applies it with swapTypespecPointersInUhdm
      (body :554-637), which rewrites every expr's Typespec across the WHOLE
      serializer (:632-634 — a `variables` IS-A `expr`).  The clone's
      ref_typespec points at ITS OWN copied object, which is not a key in that
      map.  The home is repaired; the copy never is.

   Everything the grid measures follows from this with no extra predicate:
     * the KIND of the typedef is irrelevant — nothing in the mechanism reads it
       (arm B: struct, enum, union, string, packed vector, int, alias-of-package-
       typedef and class-handle typedef all degrade);
     * the DECLARING SCOPE decides — a PACKAGE typedef resolves at first compile,
       is never registered for repair, and its copy carries the real typespec
       (arm A's controls, of the very same struct kind, in the very same body);
     * every DECLARING CLASS shape behaves alike — plain, nested, parameterised,
       and INHERITED from a base class (arm C);
     * every SITE behaves alike — tf-item, tf-item with initialiser, named begin,
       loop body, if arm, case item, fork arm (arm D);
     * the HOME's def, elab and class views keep the resolved object (arm A).
