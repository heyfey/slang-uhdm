R0 (BOTH MODES) — a `ref_typespec` the judge finds on golden's side and NOT on
ours.  The SINGULAR `SafeCompare` overload names the VALUE with `RHS: <null>`
(RESUME.md §9), and the value is the whole `ref_typespec`:

    flash_mp.sv:54   logic [AllPagesW-1:0] region_end[TotalRegions];

    LHS (golden)                                RHS (ours)
      constant 54:36-54:48 (UINT:9, size 32)      the same constant
      |vpiTypespec:                               |vpiTypespec: <ABSENT>
      \_ref_typespec (fullname …region_end)
          |vpiActual:
          \_int_typespec

  THE OWNER is the `constant` at `flash_mp.sv:54:36-54:48`, id 402917 on the
  golden side: it is the LEFT operand of the `vpiOpType:11` (subtraction)
  operation that forms the Right_expr of the `array_var region_end`'s ONE
  `vpiRange`.  `TotalRegions` is `localparam int TotalRegions = MpRegions+1`
  = 9, and golden's folded `9` carries a `vpiTypespec` -> `ref_typespec` ->
  `int_typespec` (the localparam's `int` type) while ours carries none.  The
  SIBLING constant of the same operation (`INT:1`, the literal `1`) carries no
  typespec on EITHER side, and the array_var's own `array_typespec` ref is
  present and identical on both — so the missing link is specifically the
  FOLDED PARAMETER READ inside an unpacked-dimension bound.

  THIS IS THE `typespec-linkage` FAMILY the campaign already has a memory for
  ("folded-param constant missing its int type", LocalParamInNestedForLoops).
  `constant::Compare` reads `Typespec` (generated Compare, and `VpiDecompile`
  /`VpiSize`/`VpiConstType` alongside it), so it is judge-visible; the two
  bounds' constants are otherwise byte-equal.

  THE QUESTION FOR THE NEXT PASS: when does Surelog attach a
  `ref_typespec` -> `int_typespec` to a FOLDED parameter read?  Decode
  `CompileHelper::compileExpression`'s constant-folding return path and
  `adjustSize` (earl63's `§ constCallFoldAdjustSize63` names the producer x
  consumer split), then census EVERY constant in both corpora keyed by
  (owner-kind, field) with the typespec PRESENCE as the payload — earl64's
  `allc64.cpp` every-constant span-keyed census + `msjoin64.py` and earl64's
  `tsfind64.cpp` typespec-presence probe are the instruments to reuse, and
  earl62's `mlts62.cpp`/`tscen65`/`tsdet65` are the typespec-presence readers.
  Predict the movers from the PRISTINE databases first: the shape is narrow
