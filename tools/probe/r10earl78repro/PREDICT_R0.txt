WHICH ARM.  `expr::Compare` (UHDM/build/generated/src/expr.cpp:83-102) reads
`VpiDecompile` first -- "3" == "3" -- then `VpiSize`.  64 != 32, so THE FAILING
FIELD IS `vpiSize` and no typespec is ever reached.  Both sides are non-null
constants of the same kind, so BaseClass.h's `(lhs != nullptr) && (rhs !=
nullptr)` arm names both.  Read the MK line, not the shape (RESUME §9).

WHERE IT LIVES.  The object is the LEFT operand of the `+` in an UNPACKED-ARRAY
DIMENSION of an `array_var` declaration:

    array_var tl_u_o (126:24)
      -> range (126:32)
        -> operation `+` (126:32-126:35)
          -> constant  <-- THE HEAD (the folded read of `N`)
          -> constant 1

`N` is `tlul_socket_1n`'s `parameter int N = 1` overridden per instantiation.
The head is reached through `u_spi_device.u_reg.u_socket` first, but the SAME
defect is present in every instantiation of `tlul_socket_1n` in the design
(`findspan78 <db> 126 32` lists spi_device N=3, flash_ctrl N=4, hmac N=3,
usbdev N=3, ... -- golden sizes every one of them 64, we size every one 32).
It is therefore a FAMILY, not a single cell, and the family is wholly inside
one declaration site.

WHAT THE NEXT PASS MUST MEASURE FIRST.  The size 64 is Surelog's UNSIZED
parameter-read fold (`CompileHelper::getValue` mints straight off the `Value`
with no `adjustSize` consumer above it -- the same 64 earl68 decoded for the
whole-Rhs genvar fold), while ours re-encodes at the parameter's declared `int`
width.  The SPAN differs too (golden claims only the `N` token, we claim the
whole `N+1`), which says the two producers fold at different NODES: golden
reduces the OPERAND, we reduce and re-span at the operation.  Census every
range bound of every packed and unpacked dimension, split by (parameter read /
expression over a parameter / literal) and by declaration kind (array_var,
packed logic_net, port, struct member), before touching the encoder -- the same
encoder serves all of them, and § srlgFoldNaturalWidth / § adjustSize already
own the neighbouring cells.
