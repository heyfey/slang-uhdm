Run each with tools/probe/r10uvm11run.sh (re-point W to your worktree):
  r10uvm11run.sh <reprodir> <tag>   ->  /tmp/r10uvm11_<tag>_{gd,sd,ge,se}.uhdm

t1  § classLoopVar11 — THE R5 HEAD.  `for (Inner it = h.first(); it != null;
    it = h.next())` — a for header whose loop variable has a CLASS type.
    StmtEmit's ForLoop arm accepted only PredefinedIntegerType and 4-state
    logic loop vars and otherwise did `noteUnsupported("for loop var type")`
    + `return nullptr`, so the ENTIRE for statement — header, condition,
    increment and body — was dropped.  That is why golden built
    `hier_path[ref_obj cbs, method_func_call first]` 244 times and we built
    4: the calls were never reached, not mis-shaped.  UVM writes this shape
    at 35 source sites (`uvm_reg_field.svh:1135`, every `uvm_vreg` /
    `uvm_reg_cbs` twin, `uvm_callback_defines.svh`).  Golden gives the loop
    variable the ordinary statement-scope object kind (class_var written
    directly, string_var for `for (string sv = "a"; ...)`) and keeps the
    init-assignment shape the integral arms already produced, so the fix is
    `makeReturnVar` for the non-integral case and nothing else.
    Controls in the file: int loop var (b), externally-declared class loop
    var (c), plain statement/expression calls (d), class loop var with a
    NON-call `null` initialiser (e — the TYPE alone is the discriminator,
    not the initialiser), string loop var (f).
    BYTE-IDENTICAL to golden in BOTH views after t2's laws land too.

t2  § deepRecvCall11 + callParenSpan11 — a class-method call whose RECEIVER
    is more than one bare name.  Both arms of the class-method path keyed on
    `recv0.kind == NamedValue`, so `m.l.doit()`, `m.la[2].doit()` and
    `m.l.get()` all fell through to the flat method_func_call.  Golden:
      EXPRESSION position -> hier_path `<recv>.<method>` whose elements are
        one NAME-ONLY ref_obj per plain segment, a bit_select per INDEXED
        segment (bare name, vpiFullName = the written path through the index
        — `q[0]`, `m.la[2]` — and an UNPARENTED index constant), then the
        method_func_call.
      STATEMENT position -> Surelog's compileTfCall reads only the FIRST TWO
        names: the call is named after segment 1, segment 0 is the scoped
        vpiPrefix, the method's own arguments are DROPPED, and an index on
        segment 1 becomes the call's single vpiArgument (`m.la[2].doit();`
        -> method_func_call `la`, prefix `m`, vpiArgument 2).
    The SINGLE-segment forms were already right and are untouched:
    `q[0].doit();` keeps method_func_call `doit` prefix `q`.
    § callParenSpan11 (found here, applies to both hier_path arms): slang's
    CallExpression range stops at the callee name when the call takes no
    arguments (`h.first` for `h.first()`), Surelog's hier_path runs through
    the closing paren — take the invocation SYNTAX range when it starts at
    the same place and reaches further.
    s_calls / e_calls BYTE-IDENTICAL after; the file's only residue is the
    `int q[$]` class property (a queue-property shape, unrelated).

t4  § thisRecvCall11 — a `this.`-ROOTED receiver, and the CORRECTION to t2's
    first cut.  UVM's TLM ports/exports are generated by
    `UVM_GET_IMP(this.m_if, T, t)`, so every forwarding method calls
    `this.m_if.can_get()`; t2's flattener made `this` a path segment and
    built a 3-element hier_path for each, +2011 hier_path elements on
    SeqDriver where golden's whole delta was +838, and golden emits ZERO
    elements there.  Read off Surelog CompileExpression.cpp
    `compileComplexFuncCall` :5154-5252 (`compileTfCall` hands every
    `paImplicit_class_handle` straight to it) — rootName is "this" and the
    arm is chosen by what FOLLOWS the first name:
      List_of_arguments  (`this.m(args)`)      -> method_func_call named
        after the METHOD, vpiPrefix a STRING constant "this" (size 4,
        vpiStringConst) — the handle compiled as the prefix EXPRESSION;
      Constant_bit_select (`this.a.m()`, `this.a[i].m()`, STATEMENT) ->
        `fcall->VpiName(rootName)`: the call is literally NAMED "this",
        located at the FIRST name after it, same string-constant prefix,
        and the method's own arguments ride it (s_this_args);
      slStringConst (`this.a.m()`, EXPRESSION) -> a one-line MOCKUP in
        Surelog: a bare constant carrying ONLY VpiDecompile("this") — no
        value, no size, no const type — spanning the whole call;
      Select (`this.a[i].m()`, EXPRESSION) -> the fallback hier_path:
        ref_obj "this" located at the FIRST name, then one ref_obj per
        remaining name INCLUDING the method (never a method_func_call),
        indices dropped from the path name (`this.arr.get`).
    Both "this" constants are UNPARENTED.  `super.`-rooted is the same
    Surelog arm with rootName="super" but is NOT measured here, so it is
    excluded from the deep path and keeps its pre-existing flat form.
    All nine subroutines BYTE-IDENTICAL after; the file's residue is the
    `Inner arr[4]` class property (unpacked-array-of-class), unrelated.
