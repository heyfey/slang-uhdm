== FINDINGS AGAINST THE PASS (none is a regression; the patch is unchanged) ==

V1  ct182pred IS UNSOUND, AND ITS "provably cannot move" CLAIM IS FALSE.
    It requires the candidate element's Actual_group to be NULL in the pristine
    bytes.  But bindBuiltin182 runs BEFORE bind9, so an element that pristine's
    bind9 bound to a BODY LOCAL of the same name is a mover whose pristine actual
    is NOT null - which is arm C cell C3, one of the pass's own headline cells.
    MEASURED: ct182pred prints "CANDIDATES 0" on the pass's own arm-C pristine
    database, which does move.  v182pred.cpp here drops the null requirement and
    excludes instead only the actual kinds pkgCloneMember10 produces
    (typespec_member) and an already-minted func_call; on arm C it finds the two
    C3 candidates (act=int_var).  Re-swept over 956 + 1358 pristine databases it
    returns the SAME answer as the pass claimed - 4 (SeqDriver x2, MiniAmiq x2)
    and 0 - and all 8 corpus candidates carry act=<null>, so the blind spot has
    no corpus instance and the headline prediction stands.

V2  THE bit_select COMMENT IS WRONG, AND GOLDEN MINTS WHERE WE DO NOT.
    The patch's comment says a bit_select predecessor "takes its own arm in that
    walk and never reaches the mint".  bit_select, part_select and
    indexed_part_select are all declared "final : public ref_obj", so DeepClone's
    any_cast<ref_obj*>(previous) SUCCEEDS on a bit_select and the mint IS reached
    through it.  MEASURED on v182_f_recv: for a queue-of-queues in a clone body,
    "mullion[0].size" binds a minted func_call(size) in GOLDEN and stays bare in
    both our binaries.  Pristine was bare too, so this is a MISS, not a
    regression, and the exact-uhdmref_obj gate is the conservative choice.
    Corpus mass 0: no corpus candidate has a bit_select predecessor.

V3  R3 IS STRONGER THAN STATED.  packed_array_var is not merely unreached, it is
    UNREACHABLE from legal source: slang refuses ".size"/".max" on a packed array
    ("invalid member access for type 'logic[3:0][7:0]'").  array_net and
    packed_array_net cannot be a clone-body predecessor at all, because a package
    clone body's declarations are variables and never nets.  Those three arms of
    arrayActual182 are dead code - harmless, and correctly modelled if ever live.

V4  TWO OF THE BRIEF'S FACES ARE NOT EXPRESSIBLE.
    "chained q.max.something": slang rejects it - "parentheses are required when
    chaining method calls" - and the parenthesised spelling makes every element a
    method_func_call, which the law refuses.  ".max"/".min" on a struct-element
    queue: "array method 'max' can only be called on unpacked arrays of comparable
    values", so "size" is the only mint name a struct-element queue can reach,
    which is exactly the cell arm C measures.

V5  NOT THIS PASS.  Earlgrey_0_1/testflags carries two ORPHAN func_calls under a
    hier_path in OUR database and none in golden (region_cfgs[8].size.q and
    region_cfgs_i[i].size.q).  They are present IDENTICALLY in the pristine
    binary, so they predate this patch, and an orphan is reachable only through
    the dump tail the judge never walks.
