## 2. THE DECODE (question 2)

### 2a. R0 — the producer's elaborated cell is a `clone_tree`, not a rebuild

`UhdmWriter::writeCont_assign`
(`~/git-repos/Surelog/src/DesignCompile/UhdmWriter.cpp:2246-2277`):

```cpp
if (res && (res->UhdmType() == uhdmconstant)) {
  if (cloned == false) {
    ElaboratorContext elaboratorContext(&s, false, true);
    assign = (cont_assign*)UHDM::clone_tree(assign, &elaboratorContext);
    assign->VpiParent(m);
    …
  }
  assign->Rhs((constant*)res);            // ONE field is swapped
}
```

A `clone_tree` copies the WHOLE object, so `VpiNetDeclAssign`, `VpiStrength0`,
`VpiStrength1` and `Delay` ride into the elaborated view by construction. Our
elaborated-interface clone was built field by field and carried the parent and
the span alone. All four are read by `cont_assign::Compare`
(`~/git-repos/UHDM/build/generated/src/cont_assign.cpp:104-124`) **BEFORE** the
Rhs, so the gap is judge-visible ahead of everything the fold decides.
r11v83 landed the copy for the cells pass 83 newly cloned; this widens it to
every clone the branch builds, which is what `clone_tree` does.

### 2b. R1/R2 — in an interface home NOTHING re-stamps the reduce, so golden's
### folded Rhs IS the elaborated parameter operand

The same `writeCont_assign` runs `adjustSize` **only when `tps` is non-null**,
and `tps` comes from the Lhs ref's own typespec or from the variable
`CompileHelper::bindVariable` found. `bindVariable` (`CompileStmt.cpp:3089`)
switches on function / task / begin / **module_inst** only and stops dead at an
`interface_inst` — which is `caLhsAdjustBind106`'s already-landed decode. So in
an interface home the elaborated cell carries the RAW reduce.

**And the raw reduce is the parameter's own pattern operand.** Arm
`x3_exprkinds` proves the identity row for row: for every one of its ten
instances the cont_assign's folded Rhs is byte-identical to that instance's
`param_assign` operand for the member —

```
PARAM work@dut.u_lit  constant|DEC:7|sz=8|dc=8'd7|ct=1         CA y  constant|DEC:7|sz=8|dc=8'd7|ct=1
PARAM work@dut.u_nam  constant|INT:2|sz=8|dc=<nodc>|ct=7       CA y  constant|INT:2|sz=8|dc=<nodc>|ct=7
PARAM work@dut.u_cat  constant|BIN:00010010|sz=8|dc=<nodc>|ct=3  CA y  constant|BIN:00010010|sz=8|dc=<nodc>|ct=3
```

so R1 and R2 are two readings of ONE fact: our emitter re-derives the value
where the producer copies an operand.

**R1, the width.** The member-width stamp is `CompileHelper::adjustOpSize`, and
it reaches the OUTERMOST pattern's operands only. Measured on `n1_ifnest`
(one interface, nine cells, three Lhs widths per shape):

| read | depth | member | golden | ours (base) |
|---|---|---|---|---|
| `C.n` | 1 | `int unsigned` | `UINT:6 vpiSize:32`, ONE shared object for the 8-, 32- and 64-bit Lhs alike | 32 |
| `D.inner.n` | 2 | `int unsigned` | `UINT:11 vpiSize:64` at every Lhs width | **32** |
| `D.inner.m` | 2 | `logic [7:0]` | `HEX:5A vpiSize:8` | 8 |
| `E.o2.inner.n` | 3 | `int unsigned` | `UINT:21 vpiSize:64` | **32** |
| `E.o2.t` | 2 | `logic [3:0]` | `HEX:2 vpiSize:4` | 4 |

The flat row settles that the Lhs is not consulted in this home AT ALL (one
object serves three Lhs widths). `n3_nestkinds` crosses the nested member's
KIND — `byte`, `logic [7:0]`, `logic [11:0]`, `longint unsigned` all read their
written literal's own width on both sides, and only the two members written as
UNSIZED DECIMALS (`int`, `int unsigned`) read 64 where we wrote 32: an unsized
decimal operand is 64 bits wide until something stamps it, and at depth >= 2
nothing does. `n6_refnest` fences the rule — the inner level reached through a
NAMED localparam (`inner: INNERLIT`) reads 64 exactly as a written inner
pattern does, so the count is the READ's depth, not "was a pattern written
here".

**R2, the spelling.** `x3_exprkinds`, ten instances of one interface, one
element form each:

```
`8'd7`            DEC:7        vpiDecompile:8'd7      (the written literal)
`KB`              INT:6        vpiDecompile:6
`KB + 8'd1`       INT:7        vpiDecompile:7
`-KB`             INT:-6       vpiDecompile:-6
`KB > 2 ? 3 : 4`  DEC:3        vpiDecompile:8'd3      (the chosen literal)
`8'(K)`           INT:2        **no vpiDecompile**
`8'(K + 3)`       UINT:5       **no vpiDecompile**
`8'(9)`           UINT:9       **no vpiDecompile**
`8'(-K)`          UINT:254     **no vpiDecompile**
`{4'h1, 4'h2}`    BIN:00010010 **no vpiDecompile**
```

So it is NOT "computed" that drops the spelling — an arithmetic element keeps
one and we already match it (`u_op`, `u_un` are MATCH on the pristine binary).
It is the explicit SIZE CAST and the CONCATENATION, and nothing else in the
grid. A replication is not included: no arm measured one, and GOLDEN WRITES
NOTHING ON A MISS cuts both ways.

### 2c. The homes, separated by measurement

`n5_nestsel` asks whether R1 is the interface home's or every home's: a MODULE
body reading `D.inner.n` onto a SELECT Lhs, where `writeCont_assign` fills no
`tps` either. **Golden reads `UINT:11 vpiSize:64` there too**, so the producer's
rule is home-INDEPENDENT. Our module home DECLINES that cell (the landed
whole-name Lhs fence), so widening would change nothing there today — which is
why the gate names the interface homes and the other homes' would-be sites are
CENSUSED (§6: zero in both corpora) rather than assumed.

`n4_nestgen` measures both of an interface's homes on ONE nested read — the
body cell and the gen-scope cell read golden's 64 alike — so the interface body
site and the gen-scope site take one answer. `x5_ifgenexpr` does the same for
R2.

### 2d. The instrument this pass had to build first

r11v83 §3 convicted the pass-83 per-cell scorer: its key was (owner, span, Lhs
name, Rhs kind, Rhs value) and it read **none** of the four drive fields, so it

## 4. THE THREE LAWS, GATED (question 4)

### § caIfaceCaCloneKeepsDriveFields85 (`R11U85_DRIVE_OFF=1`)

> The elaborated-interface `cont_assign` this branch builds is the producer's
> `clone_tree` of the def cell, so it carries `VpiNetDeclAssign`,
> `VpiStrength0`, `VpiStrength1` and `Delay` — on EVERY shape it clones, not
> only the ones r11u83 newly routed into it.

The gate is the switch alone: with it set, the copy falls back to r11v83's
`sps83`-only condition, which is the base's behaviour byte for byte.
**Not widened beyond the copy**: `VpiNetDeclAssign` is copied because
`clone_tree` copies it, but our interface DEF listing carries no
net-declaration-assignment cell at all (`a3_ndassign`), which is a LISTING law
with its own decode and its own census — §8 R0, not smuggled in here.

### § caIfaceCaFoldNestedOperandWidth85 (`R11U85_NESTW_OFF=1`)

> The member-width stamp is the producer's `adjustOpSize` and it reaches the
> OUTERMOST pattern's operands only; a member read through a NESTED pattern
> keeps the operand's own width.

Gated to `ifaceHome85 && chain85 >= 2 && !bind55`. `bind55` is READ, not
ignored: where an `adjustSize` will run the stamp is invisible anyway, and
leaving it in place keeps every landed `vpiDecConst` cell — whose `adjustSize`
arm does not re-size — byte-identical. The depth is `caSetterChainDepth85`,
the same member chain `caStructParamSetter55` walks.

### § caIfaceCaFoldCastOperandNoDecompile85 (`R11U85_CASTDC_OFF=1`)

> An element written as an explicit SIZE CAST or as a CONCATENATION folds with
> no `vpiDecompile` in the interface home, and `constant::Compare` reads
> `VpiDecompile` first.

Gated to `ifaceHome85 && chain85 >= 1 && castOrConcatSetter85(setter)`. Only
the SPELLING is dropped; the value, the width and the encoding stand exactly
where the landed laws left them, so a form this pass does not decode stays a
measured residue and moves no further from golden than it already was.

`R11U85_OFF=1` drops all three. `R11U85_CELLDBG=1` traces every clone the
interface branch builds (`R11U85DRIVE`, with the four fields the def cell
carries) and every cell reaching the substitution emitter **in every home**
(`R11U85SUBST`, with chain depth, home, bind, and both gates' answers) — the
homes the gate EXCLUDES included, so one run of one binary predicts the mover
set and censuses the residue population in the same pass.
