  WHICH ARM.  Read the MK line: both sides are non-null `param_assign`s, so
  `param_assign::Compare` runs; its `Rhs` slot holds an `operation` on the left
  and a `constant` on the right — two non-null objects of DIFFERENT `UhdmType`,
  i.e. `BaseClass.h:188`'s two-non-null arm, a KIND mismatch inside
  `BaseClass::Compare`'s `VpiType` line.  `vpiOverriden` is a SECOND, separate
  disagreement on the same object (golden does not set it on this localparam);
  decide which one `param_assign::Compare` reads FIRST from the generated
  source before naming the field.

  THE DECODE TO START FROM.  Golden reduced the INNER sub-expression
  (`('h1 << WordsBitWidth) - 1'b1` -> `INT:255 sz64 ct7`) and then STOPPED: the
  outer `~` (unary bitwise negation) is still an `operation`, carrying the
  parameter's own located `logic_typespec` as its typespec.  We reduce the
  whole thing, mask it to the declared 17 bits and emit `UINT:4294967040`.  So
  the question is WHY `UHDM::ExprEval::reduceExpr`'s unary-not arm bails here —
  the operand is an unsized/`'h1`-derived value whose width ExprEval cannot
  name, which is exactly the class of abstention § srlgNegLitGetValue30 and
  earl83's R2 (the `1ULL << W` UB) already touched from other sides.  The DEF
  copy and the DEFAULT-mode LHS differ in shape (default's LHS is a deeper
  `opType 11` over `opType 22` nest, testflags' is the single `opType 4` over
  `INT:255`), so measure BOTH modes before writing the rule.
  `BankAddrMask` on the very next line (flash_erase_ctrl.sv:42) is the same
  shape one operator deeper and is the obvious second cell.
