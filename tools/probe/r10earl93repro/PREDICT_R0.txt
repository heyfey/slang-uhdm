FIVE MEASUREMENTS SAY IT IS NOT THE LAW:

  1. `R10E93_OFF=1` ON THE PATCHED BINARY REPRODUCES THE PATCHED VALUE, not the
     pristine one.  The law's install is switched off and the number does not

  3. `R10E93_CELLDBG=1` reports NO reached cell in this file -- the site the

  4. earl92's committed `BOUNDARY_WIDE.diff` lists the SAME file, in the SAME
     two views, as a boundary difference for a completely unrelated law
     (`plain r10buvm22repro/g22.sv`, `elab r10buvm22repro/g22.sv`).
  5. THE LAYOUT CONTROL, the decisive one.  A binary built from PRISTINE 5c6cea7
     with ONE behaviour-free line added to `ExprEmit.cpp` --
         __attribute__((used)) static char r10earl93_layout_pad[32];
     -- and NOTHING else, reproduces the PATCHED numbers EXACTLY:
         layout control  UINT:22511321  UINT:22510465
         patched         UINT:22511321  UINT:22510465
         pristine        UINT:22511289  UINT:22510433
     32 bytes of `.bss` and no law at all move the value by 32.

The number is BUILD-LAYOUT DEPENDENT: it is a value the associative-index range
synthesis reads out of memory that ANY edit to `ExprEmit.cpp` shifts (the delta

function-local `static const bool` guards of this law add).  It is a
PRE-EXISTING emitter defect the wide boundary exposes, it is invisible to both
corpora (no corpus test contains this shape), and it is filed as residue R5.

RANKED RESIDUES this pass MEASURED and deliberately did not take
========================================================================
R0  THE ELABORATED GEN-SCOPE BINDER, both heads above.  One mechanism, two
    faces (a null `Actual_group` on a net reference; a value substituted for a
    parameter reference), four source lines apart in one gen-if body.

R1  A PORT `High_conn` SIZE CAST OF WIDTH >= 64.  Golden FOLDS it -- measured
    `96'(64'hFFFF…)` -> `constant UINT:4294967295 vpiSize 96` and
    `128'(64'd11)` -> `constant UINT:0 vpiSize 128` on `g2_ctx93.sv`'s child
    instances -- and we KEEP the `vpiCastOp` operation, because
    § elabConnWrittenCastFold83 abstains at `w83 >= 64` (its own comment says
    "this law will not encode UB").  The mask this pass measured is exactly
    what that abstention was waiting for, so extending 83 to W >= 64 with
    `mask64` is now a ONE-LINE change -- but it converts an operation into a
    constant (a KIND flip, not a value flip), so it needs its own boundary and
    its own census.  3 arm cells, **0 corpus cells** (the CS family's 584
    surelog MOVED-WRONG cells contain no W >= 64 High_conn cast).

R2  A CAST INSIDE AN OPERATION.  `64'(64'd1) + gi`, `64'(x) | 64'd1`,
    `EN ? 64'(1) : 0`, `{64'(1)}`: golden masks the INNER cast and then runs
    the operation on the wrapped value, so `g3`'s gen-for `L_genfor` is 0/1 on
    golden and 1/2 for us.  Reproducing it needs ExprEval's whole `reduceExpr`,
    not a mask.  4 arm cells (`g3 L_genfor` x2, `g5 s_in_add/s_in_or/
    s_in_tern/s_in_cat`), 0 corpus cells.
    The same residue covers the ONE nest shape slang collapses out of the AST:
    `32'(65'(all-ones))` is golden 1 and ours 4294967295 (`g7 n_32_65`),
    unchanged by this law because the inner 65 is not in the AST at all.

R3  THE SIGNED ARM.  ExprEval's `oper_signed` branch mints `INT:` and a signed
    `logic_typespec`, and above 64 bits it does not sign-extend; golden's
    `64'(-1)` is `UINT:0` and `96'(64'shFFFF…)` is `INT:4294967295 vpiSize 1`
    where we emit `INT:-1` at the cast width.  Wrong at 32 and 63 as well as
    above 64, i.e. a PRE-EXISTING family this law deliberately does not enter.
    16 arm cells (`g1 c_*_n` x8, `g4 k_s64/k_s96/k_sd64/k_sd96`), 0 corpus
    cells.

R4  THE `get_value` BAIL AND THE TYPEDEF TARGET -- two shapes where GOLDEN
    KEEPS THE WHOLE CAST and we fold anyway: an operand constant encoded
    BIN/HEX/OCT with `VpiSize() > 64` (the bail is on the SIZE, not the value:
    `96'(96'h0000_0000_FFFF_FFFF_FFFF_FFFF)` bails while `96'(96'd5)` folds),
    and a vector TYPEDEF cast target (`w64_t'`, `b64_t'`).  Pre-existing
    over-folds; this law changes the value it writes in a bail cell from one
    wrong number to another and the cell stays STILL-WRONG.  ~23 arm cells,
