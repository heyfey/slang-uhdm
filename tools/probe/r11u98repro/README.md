## 3. QUESTION 2 — the decode, in the pinned sources

### LAW A — the listing IS `std::multimap<std::string, ClassDefinition*>`

`UhdmWriter::writeClasses`
(`~/git-repos/Surelog/src/DesignCompile/UhdmWriter.cpp:1078-1084`) walks a
`ClassNameClassDefinitionMultiMap` straight into the home's vector —
`m->Class_defns(dest_classes)` at :1465 (module) and :1848 (program) — and
that type is

```cpp
// ~/git-repos/Surelog/include/Surelog/Common/Containers.h:33-34
using ClassNameClassDefinitionMultiMap =
    std::multimap<std::string, ClassDefinition *, StringViewCompare>;
// :12-18
struct StringViewCompare {
  constexpr bool operator()(std::string_view a, std::string_view b) const {
    return a < b;                     // a BARE lexicographic byte compare
  }
};
```

keyed by the **BARE** class name: `mdef->addClassDefinition(name, def)` at
`ResolveSymbols.cpp:194` (module) and `:156` (program), both passing `name` —
not the `fullSubName` that goes to the FileContent map one line above.  So the
listing golden writes is that map's order, full stop.

**MEASURED, not assumed** — four arms that separate `std::string::operator<`
from every friendlier ordering it could have been (every golden regenerated by
the pinned Surelog v1.87):

| arm | declared | golden lists | what it rules out |
|---|---|---|---|
| `g5_modclassthree` | Mclass, Zclass, Aclass | **[Aclass, Mclass, Zclass]** | a swap of the first pair — it is a FULL sort |
| `g6_modclasscase` | b_cls, Z_cls, A_cls | **[A_cls, Z_cls, b_cls]** | case-INSENSITIVE order ('A'=65 < 'Z'=90 < 'b'=98: BYTE order) |
| `g7_modclassdigit` | c9, c10, c2 | **[c10, c2, c9]** | natural/numeric order — it is LEXICOGRAPHIC |
| `g8_modclassprefix` | ab, a, _z | **[_z, a, ab]** | any identifier-ish order: '_'=95 < 'a'=97, and the shorter prefix first |

**THE POSITIVE CONTROL that the model is the map and not a guess about
sorting:** the PACKAGE home and the DESIGN ROOT are name-keyed at the base
already (`emitPackageClasses` and the `AllClasses` block, both
`src/UhdmExporter.cpp`, both landed earlier), and `g4_pkgclassnames` — the
IDENTICAL source shape in a package — reads **cmp rc=0 on the pristine
binary**.  Only the module/program home was left in source order.

r11u95's verifier landed § `caProgClassListNameKeyed95V`, the same comparator
but reached only from inside the program flattening switch
(`if (clist95.size() != own95)`).  LAW A generalises it to the LISTING, which
is the thing the map was always a property of.  That landed sort is left in
place untouched: same key, stable, a no-op once LAW A runs, and it is what
`R11U98_OFF=1` falls back to.

### LAW B1 / LAW B2 — the class-home road is NOT `collectObjects_`

Pass 95 decoded the program's member flattening out of
`CompileProgram::collectObjects_`, and its module controls (`c1`, `c6`, `c9`)
read 0 because the MODULE and INTERFACE collectors DO stop at generate nodes.
The brief asks where these classes travel instead.  **They never go through a
collector at all.**  `ResolveSymbols::createFastLookup`
(`~/git-repos/Surelog/src/DesignCompile/ResolveSymbols.cpp:72-210`) files every
class in the design at PARSE-RESOLVE time, from the raw syntax tree, before
any compile:

```cpp
// :79-90  the file-level walk
  VObjectTypeUnorderedSet types = {
      paModule_declaration, paPackage_declaration, paConfig_declaration,
      paUdp_declaration,    paInterface_declaration, paProgram_declaration,
      paClass_declaration};
  VObjectTypeUnorderedSet stopPoints = {
      paModule_declaration, paPackage_declaration,
      paProgram_declaration, paClass_declaration};   // NO INTERFACE
  std::vector<NodeId> objects =
      m_fileData->sl_collect_all(m_fileData->getRootNode(), types, stopPoints);
```

* **A MODULE** is a stop point, so its classes are not seen at file scope;
  the `paModule_declaration` case (:166-201) runs its OWN whole-subtree
  collect whose only stop points are `{paClass_declaration,
  paModule_declaration}` — **a generate region is not one** — and files each
  hit BOTH as `work@<mod>::<Class>` in the FileContent map and as the BARE
  name on the module: `mdef->addClassDefinition(name, def)` (:194).  That is
  LAW B1.  A `paProgram_declaration` (:135-158) does the same with the stop
  set `{paClass_declaration}`, which is pass 95's class face.
* **AN INTERFACE** is NOT a stop point and has no case of its own — it falls
  to `default:` at :203-209, which builds a `ModuleDefinition` and collects no
  classes.  The file-level walk therefore descends INTO the interface, reaches
  the class declaration (in the body or in a generate block, indifferently),
  and files it through the bare `paClass_declaration` case at :160-166:

  ```cpp
      ClassDefinition* def = new ClassDefinition(fullName, lib, nullptr, ...);
      m_fileData->addClassDefinition(fullName, def);   // fullName = work@C
  ```

  with a **NULL container** — which is exactly why the name is `work@C` and
  not `work@ifc::C`.  `CompileDesign::collectObjects_`
  (`CompileDesign.cpp:272-277`) copies every FileContent class into the
  design, and `UhdmWriter` publishes it at :5181-5194 under
  `if (!c->VpiParent()) writeClass(classDef, v4, s, d);` — first-writer-wins,
  and nobody wrote this one because it has no home.  That is LAW B2, and the
  SAME test is why a module's or a program's class is NOT there.

Nothing on either road evaluates a generate condition or a genvar, and the
grid reads all three consequences on the module home (§4b): an untaken
`if (0)` arm is listed, a two-iteration `for` lists ONE copy, a class two
blocks deep is listed.

### LAW B3 — one missing `SyntaxKind` in one item filter

`emitDefGenStmts`'s branch body (`src/ModuleEmit.cpp`) filtered the items it
would turn into def-view processes down to five syntax kinds — `AlwaysBlock`,
`AlwaysCombBlock`, `AlwaysFFBlock`, `AlwaysLatchBlock`, `InitialBlock` — and
`FinalBlock` was not among them, so the `named_begin` we correctly built for
`if (1) begin : g final begin … end end` got an EMPTY `vpiStmt`.
`emitProcess` already emits a `final_stmt` correctly: the ELABORATED
`gen_scope` copy of the very same construct is byte-equal to golden's at the
base.

The new arm claims only the homes that KEEP their generate placeholders.  A
`program` def keeps none — `UHDM::program` carries no `gen_stmts` relation, so
`instSetGenStmts` (`src/EmitHelpers.h:2997-3004`) drops the whole `regions`
vector for a program home and everything `emitBranch` built for it is
unreachable.  Measured, and it is the pass-95 controls that measured it: an
unrestricted arm mints a `final_stmt` subtree into five program arms
(`a2_progfinal`, `a18_proggenmixed`, `x14_proggentwoblocks`,
`x19_proggenfinalorder`, `x20_progtopgenclass`) whose id-normalised dumps stay
**IDENTICAL** — the move is serializer arena/ids alone, an object nobody can
reach.  A Make call is a write; the restricted arm moves none of the five.

### THE SCORE, PER CELL AND PER SUBTREE

## 8. RESIDUES (ranked)

1. **A MODULE/PROGRAM HOME DOES NOT LIST ITS PARAMETERIZED CLASSES.**
   `g9_modclassparam`, 159 cmp lines, identical on both binaries.  A module
   body declaring `class Zclass`, `class Pclass #(int N = 1)` and
   `class Aclass` is listed by golden as **`[Aclass, Pclass, Zclass]`** — the
   parameterized declaration is a first-class member of the name-keyed map,
   compiled once from its default specialization.  slang models it as a
   `GenericClassDefSymbol`, not a `ClassType`, and the def-view listing in
   `src/ModuleEmit.cpp` collects only `ClassType`, so we list neither copy.
   The DESIGN ROOT (`src/UhdmExporter.cpp`'s `AllClasses` block) and the
   PACKAGE home (`emitPackageClasses`) both already handle it, through
   `getDefaultSpecialization` — the same two lines would serve here, and they
   belong to a pass that can measure the arena consequences of minting a
   specialization during the DEF phase.  LAW A still improves the arm (CELL
   DIFF 2 -> 1, CELL OK 0 -> 1, OURS-ONLY 0 throughout).  CORPUS-INVISIBLE:
   no corpus home in either suite is reached at all (§6).  **R0.**
2. **THE r11u95 / r11v95 RESIDUES THIS PASS DOES NOT TOUCH, unmoved and
   accounted for**: `a20_proggenparam` 72 (r11u95's R0, the program's
   generate-block PARAMETER, fenced in `src/ParamEmit.cpp` — the sister
   pass's ground); r11v95's `x12_proggenimportfn` 203 and
   `x26_progimportbodyfn` 241 (R3, the def view's imported package
   subroutine); `x2_proggenassert` 64 (R4, a concurrent assertion in a
   program's generate block); `x8_proggendupname` 14 (R5, the name-keyed
   task/func registry keeps the FIRST span and the LAST body); `n11_ansistr`
   113 and `pa9_proggenparam` 72 on the r11u93 grid.  All read the same on
   both binaries, and the r11u93 grid is **53/53 `cmp`-identical**.
3. **THREE CENSUS ARMS SEGFAULT, ON BOTH BINARIES**: `Rggen`/testflags and
   `Tnoc` in both modes read `rc=-11` under the census driver's `-o /dev/null`
   replay on the PRISTINE binary and on the law binary alike.  `Rggen`/
   testflags is `SURELOG_FAIL` and `Tnoc` is `SLANG_REJECT` in
   `results/golden_surelog.csv`, so those arms teach error recovery, not
   golden.  Pre-existing; recorded, not fixed.
4. **A PROGRAM DEF STILL BUILDS GENERATE PLACEHOLDERS NOBODY CAN REACH.**
   `emitDefGenStmts` runs in full for a program home and `instSetGenStmts`
   then drops the whole `regions` vector, because `UHDM::program` carries no
   `gen_stmts` relation.  That is pre-existing (the base binary does it too)
   and invisible to the judge; LAW B3 declines to add to it (§3).  Cleaning it
   up would shrink a program's serialized arena and is worth a pass of its
   own, with the byte pins re-measured.  **Recorded.**
