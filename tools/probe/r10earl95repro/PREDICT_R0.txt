    hmac_pkg.sv:17   typedef logic [31:0] sha_word_t;
    the object is the `logic_typespec` at 17:11-17:23 reached through
    work@top_earlgrey.u_hmac.

      LHS (golden) logic_typespec  VpiName `sha_word_t`
                                   VpiParent -> ref_typespec
                                     (work@top_earlgrey.u_hmac.sha_word_t)
                                   VpiInstance -> package hmac_pkg
      RHS (ours)   logic_typespec  VpiName `hmac_pkg::sha_word_t`
                                   VpiParent -> module_inst work@top_earlgrey.u_hmac
                                   VpiInstance -> package hmac_pkg

    Same kind, same range (31:0, both constants identical), same instance --
    the head is `VpiName`, and `typespec::Compare` reads it.

    FOUR MEASURED FACTS, the decode this pass hands over:

    1. IT IS PRE-EXISTING, NOT INTRODUCED.  `ln95 <db> 17 logic_typespec` on the
       PRISTINE database prints `hmac_pkg::sha_word_t` for every copy, exactly
       as the patched one does.  The prim_lfsr head was masking it.
    2. IT IS A NAMING HEAD, AND NAMING IS CONTEXT-DEPENDENT.  The campaign's
       memory records `pkg::pkg::`-style requalification as a DEAD END when
       applied uniformly (it breaks goldens and RefPkgParamInEnum); this cell
       must be decoded per-context, from `UhdmWriter`'s typespec writer, before
       any rename.
    3. THE PARENT DIFFERS TOO, and `no generated Compare reads VpiParent`
       (RESUME §9), so the parent is a CLUE, not the head: golden reaches the
       typespec through a `ref_typespec` named
       `work@top_earlgrey.u_hmac.sha_word_t` -- an INSTANCE-scoped alias -- while
       ours hangs the typespec straight off the module_inst.  The name and the
       owner are one decision.
    4. 112 CMP LINES IS THE SUBTREE PRINTING, NOT 112 CELLS.  uhdm-cmp prints
       the whole failing object twice per side; the head is ONE field.
