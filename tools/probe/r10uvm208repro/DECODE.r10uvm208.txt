4.  DECODE — SLANG-UHDM, WHERE THE SHARED OBJECT ARISES AND WHERE THE

==========================================================================
Our emitter memoises the element chain per element TYPE, not per declaration —
which is why on MiniAmiq ONE `array_typespec` serves five `local_addr`
declarations at four different source lines in `uvm_pkg` AND the clone body's
`local_addr` in `svaunit_pkg`.  The sharing is in the ELABORATED listings; in
the DEF listings the clone's chain is already clone-exclusive (owner mask 1),
which is why § 205's re-point already carries the DEF view and § 208 changes
nothing there.  Measured: § 205's own arm C (`g205_c_share`), the arm it built
to reproduce R1, scores STILL-WRONG 1 def / 2 elab on the base commit and
STILL-WRONG 0 in both views under this law.

The hook is the END of § 205's own block in `src/TypeEmit.cpp`, inside the same
`if (!pkgImportCloneTfs16.empty())` guard, so every fence is literally the same
code:

  * `declTf205` — the climb from a declaration to its innermost enclosing
    subroutine, stopping at `class_defn` / `package` / `module_inst` / `design`.
    THE CLASS FENCE, unchanged: a class PROPERTY is refused.
  * the `Return()` test — § 16's measured RETURN-VARIABLE EXCEPTION
    (r10uvm169's `g169_a_import`, r10v169's `v169_i_multi`): a clone function's
    return variable keeps the HOME's QUALIFIED target, so it counts as a

==========================================================================
(a) RE-POINT THE SHARED REF ANYWAY.  That is what § 205 refused, and the
    reason is in the `own=` column above: five HOME cells hang off the same
    object and golden keeps every one of them QUALIFIED.  A re-point moves

    home only, no clone anywhere) is BYTE-IDENTICAL on both binaries in both
    views precisely because nothing in the home world is touched.

(b) STOP MEMOISING — mint one chain per declaration everywhere, as golden
    does.  Refuted as OUT OF SCOPE for this pass by measurement, not by
    taste: it would re-mint the HOME chains too, changing thousands of objects
    across every corpus row for a difference NO generated Compare reads (no
    Compare reads VpiParent, and the shells agree in every compared field).
    § 205's R4 recorded the same asymmetry and left it standing.  The split
    changes exactly the six chains the judge scores and no others: +6
    `array_typespec` and +6 `ref_typespec` per moved row-mode, measured.
