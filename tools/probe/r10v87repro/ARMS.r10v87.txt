NOTE ON va13_genimport87 — THE ONE `RIGHT->WRONG` LINE ABOVE IS A CENSUS
ARTIFACT, NOT A REGRESSION.  DECODED FROM THE GOLDEN uhdm-dump.

va13 writes a wildcard `import pg13::*` at MODULE level AND a second one inside
a `if (1) begin : g_in` generate block that also declares its own `localparam
int GA`.  Golden therefore materializes the import copy TWICE: once in the
module instance and once in the GENERATE-SCOPE instance.  pacen87's INST key
resolves a gen-scope object to its enclosing MODULE instance, so both land on
the same census key and the multiset pairing compares OUR single row against
golden's FIRST sorted row.

The uhdm-dump says which row is which (golden, plain view):

  work@top87.u_ov          \_param_assign 5:18-5:26  |vpiOverriden:1   <- module level
  work@top87.u_ov.g_in     \_param_assign 5:18-5:26  (no vpiOverriden) <- gen scope

We emit ONE 5:18 row and it is the MODULE-LEVEL one.  PATCHED gives it
vpiOverriden:1 -- which is what golden's module-level row carries.  PRISTINE's
0 matched golden's GEN-SCOPE row by accident of sort order.  So the patched
value is RIGHT for the row it is; the real residue here is that we never
materialize the GEN-SCOPE import copies at all (6 ONLY-GOLDEN rows, pristine ==
patched).  Corpus reach of this shape: ZERO (verifier's all-cell field audit:
0 rows where we stamp and golden does not, either corpus, either view).

THE INSTRUMENT LESSON (for the next pass): a census whose INST key collapses a
generate-scope instance onto its enclosing module instance can manufacture a
phantom RIGHT->WRONG whenever golden holds more rows at that key than we do.
Read the dump before believing an R2W on an arm with ONLY-GOLDEN rows.
