== PART 1.  THE HEAD, LOCATED EXACTLY (ct83path, 116 levels, every level
   CONFIRMED against the official m_failedLhs/m_failedRhs pair)

  OWNER   unsupported_typespec(uvm_resource_types::rsrc_q_t)
          @uvm_sequencer_base.svh:1434:3-1434:23
  FIELD   Instance   (vpiInstance, compared by typespec::Compare)
  GOLDEN  package(uvm_pkg)#1   <- the ELABORATED package
  OURS    <null>

HOW THE DUMP HID IT.  The visitor prints a REFERENCED object as ONE identity
line with none of its own fields; only a decompile ROOT gets its fields.  Inside
the old head, this placeholder appears as

  \_unsupported_typespec: (uvm_resource_types::rsrc_q_t), id:25354, line:1434:3, endln:1434:23

and nothing more — literally "prints one line".  Decompiled AS A ROOT the same
object prints `|vpiInstance:` and the package under it (measured on golden
#25349 / #25354).  The leaf form is SILENT about the field, not evidence against
it.  (This pass's own first draft over-corrected to "decompile never prints
vpiInstance for a typespec", which a root decompile refuted before the patch was
finalised — the same species of error as the one being fixed, and recorded as
such.)

`SafeCompare(lhs, rhs == nullptr)` sets ONLY `m_failedLhs`, and it sets it to
the TARGET of the edge — which is why uhdm-cmp printed
`LHS: package uvm_pkg / RHS: <null>` and 1,450,011 lines of that package's
subtree while the actual defect was one null pointer on a typespec 115 levels
away.  The path (abridged; full trace in the pass log) is

  design -> AllPackages[1] (the DEF-view uvm_pkg) -> Variables[2]
  -> ... -> class_defn(uvm_sequencer_base) -> Task_funcs[..]
  -> function(start_phase_sequence) -> Variables[1] class_var(rq)
  -> Typespec -> ref_typespec -> Actual_typespec
  -> unsupported_typespec(uvm_resource_types::rsrc_q_t) -> Instance
