PART 1 — THE MOVER PREDICTION
========================================================================
TWO INDEPENDENT PREDICTORS, both computed from PRISTINE behaviour only.

(A) THE CORPUS CENSUS.  `ct92cen` enumerates, for EVERY `cont_assign` in a
    database, WHICH OBJECT its `Rhs` is in the fields the generated Compares
    actually read (operation: VpiOpType + Operands; expr: VpiDecompile /
    VpiSize / Typespec; constant: VpiConstType) — the CA family — and, for
    EVERY `operation` whose VpiOpType is vpiConditionOp, WHERE it lives and
    whether its parent still REACHES it — the CO family.  The CA key is the
    **Lhs** span, never the Rhs object this pass replaces (earl66); the CO key
    is the ternary's own span plus its context class, never a slot (earl56).
    `score92.py` joins the two sides as a MULTISET (keys collide; a
    last-writer dict drops rows).

    THE `LIVE` FIELD IS THE WHOLE POINT.  Surelog's `writeCont_assign`
    REPLACES `cont_assign::Rhs` and leaves the old ternary object in the
    serializer with its `VpiParent` intact, so a pure object census counts a
    folded ternary on BOTH sides and sees NOTHING.  `LIVE` asks whether the
    parent still points AT it — which is exactly the reachability the judge
    walks — and it is the field that flips when a fold lands.

    PRISTINE, both corpora, whole universe (409 surelog + 990 u2r databases
    that hold a cont_assign or a conditionOp; the rest have neither and are
    skipped):

R0 (BOTH MODES, THE SAME CELL) — A WIDTH-CAST LITERAL IN A PARAMETER DEFAULT
EVALUATES TO 0 ON GOLDEN AND TO 1 FOR US.

    .../Earlgrey_0_1/src/lowrisc_prim_all_0.1/rtl/prim_lfsr.sv:39
      parameter logic [LfsrDw-1:0] DefaultSeed  = LfsrDw'(1),
    instance work@top_earlgrey.u_aes.aes_prng.aes_prng_lfsr
    (instantiated from lowrisc_ip_aes_0.6/rtl/aes_prng.sv:46 with
     `.LfsrDw ( DATA_WIDTH )` where `localparam int unsigned DATA_WIDTH = 64`)

      LHS (golden)  constant 39:47-39:57  vpiDecompile 0  UINT:0  vpiSize 64
                    vpiConstType 9   Typespec -> logic_typespec 39:13-39:31
      RHS (ours)    constant 39:47-39:57  vpiDecompile 1  UINT:1  vpiSize 64
                    vpiConstType 9   Typespec -> logic_typespec 39:13-39:31

    EVERY OTHER FIELD MATCHES — the span, the size, the const type, and the
    ref_typespec's own fullname and actual.  ONLY THE VALUE DIFFERS, so the
    head is a `constant::Compare` VpiDecompile/VpiValue cell inside a
    `param_assign` (39:32-39:57), not a structural one.

  THE MECHANISM IS ALREADY DECODED — IT IS A 64-BIT SHIFT OVERFLOW IN
  `ExprEval`'s SIZE-CAST ARM.  `UHDM templates/ExprEval.cpp:4074`, the
  `vpiCastOp` case, `uhdminteger_typespec` branch, computes

      uint64_t mask = ((uint64_t)(1ULL << cast_to)) - 1ULL;
      ...
      uint64_t res = val0 & mask;

  With `cast_to == 64` — which is exactly what `LfsrDw` is in this instance
  (`localparam int unsigned DATA_WIDTH = 64`) — `1ULL << 64` is undefined
  behaviour, and on x86-64 the shift count is taken modulo 64, so the
  expression evaluates to `1`, `mask` becomes `0`, and `res` is `1 & 0 == 0`.
  GOLDEN IS THE SPEC, BUGS INCLUDED (RESUME §1): the next pass MODELS this,
  it does not "fix" it.

  THE QUESTION FOR THE NEXT PASS is therefore the FENCE, not the mechanism:
  which of our size-cast folds must reproduce the wrap and which must not.
  `cast_to == 64` is the obvious trigger, but the branch is reached only for
  an `integer_typespec` cast target whose width came from `VpiValue` or from
  `itps->Expr()`, and the SIGNED path below the mask has its own arithmetic;
  a `bit_typespec` / `int_typespec` / `long_int_typespec` target takes a
  DIFFERENT branch with no mask at all.  Census EVERY `param_assign` and
  cont_assign whose Rhs is (or contains) a size-cast operation across both
  corpora, keyed by (cast target typespec kind, cast width, view), with the
  folded VALUE as the payload, BEFORE any code; `ct92cen`'s CA walk already
  reaches every operation and needs only the param_assign owner added.  Widths
  of exactly 64 are the family; widths above 64 mask modulo 64 as well and
  must be measured, not assumed.

    encoding, width and location — when the selected arm is x/z, wider than 64
    bits, a real or a string.  Grid cells `g4 f_arm_xz`

    `g6 p_arm_real` (`EN ? 1.5 : 2.5` -> `constant@26:61-26:64`).  This pass
    installs only NON-constant arms, because minting golden's constant object
    is a different mechanism (the one § srlgCondOpInstValueTernFold9 carries
    for the select-Lhs path as `ternArm9`) and this pass would have had to
    guess its encoding.  2 arm cells, **0 corpus cells** — the trace's 1 597
    reached cells contain no instance of it.

    `decodeHierPath(..., VALUE)` = nullptr and writeCont's `&& rhstmp` refuses

    `g4 f_arm_hier` agree three ways), but the fence is stated on the ARM
    only: whether a hier_path that DOES decode to a value behaves differently
