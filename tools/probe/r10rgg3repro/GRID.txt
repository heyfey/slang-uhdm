THE CELL SOURCE (all cells share this interface unless the cell says otherwise):

  interface itf #(parameter int AW = 16, parameter int BW = 32,
                  parameter int VW = BW);
    logic [AW-1:0] a;      logic [BW-1:0] b;      logic [VW-1:0] v;

    modport mp (input a, b, v);
  endinterface

`a`  reads AW directly.   `b` reads BW.   `v` reads VW, whose DEFAULT is `BW`.
`lpm` reads the interface's OWN LOCALPARAM `LP = AW + 1`.
`recv` is the receiving module; `top` holds the interface instance(s).

THE LAW, measured cell by cell
------------------------------
(1) A REFERENCE-STYLE interface PORT VIEW re-elaborates the interface DEFINITION
    under the RECEIVING module instance: every interface parameter named in a
    member declaration takes the value of the receiving module's OWN same-named
    parameter or localparam when one exists, and the interface's declared
    default otherwise.  The CONNECTED instance's overrides are never read.
    The substitution is TRANSITIVE through the interface's own parameter and
    localparam defaults.
(2) The HOME-LIKE cell — a MODPORT-qualified port reached by a NAMED port
    connection to a NON-ARRAY instance — is the one exception: it reads the
    CONNECTED instance and is unaffected by the receiving module's parameters.
(3) An interface-ARRAY ELEMENT port view takes clause (1) UNCONDITIONALLY: none
    of the emitter's four "read the connected instance" exceptions (multi-
    parameterised def, text-multi def, aggregate-override view, generate-bearing
    interface) reaches it.

THE 6 REMAINING DISAGREEMENTS, both UNCLAIMED and both measured
---------------------------------------------------------------
1. n4_parent_has_aw (3 lines).  When the receiving module does NOT declare the
   name but an ANCESTOR does, golden's two resolution paths DISAGREE: a member's
   own range keeps the interface default (`a` = 15 although top says AW=3) while
   the interface's LOCALPARAM initializer resolves the name HIERARCHICALLY
   (`lpm` = 3, i.e. LP = top's AW + 1).  This pass consults the receiving
   instance ONLY, so n4's `lpm` stays at 16.  Neither corpus contains the shape.

   SINGLE POSITIONAL modport port view: golden takes clause (1) (4/5) but the
   emitter's `multiParamIface` exception still routes it to the connected
   instance (7/8).  Clause (3) deliberately covers only the ARRAY-ELEMENT view,
   because that is the shape Rggen and the census name; widening the exception
   for non-array views has no corpus witness in either direction and would move
   the delicate iface_param_2level / iface_cfg_mem / iface_unpacked_struct_array
   family.  NEXT HYPOTHESIS: drop `!multiParamIface && !textMultiIface9` for the
