r10v76 — WHAT GOLDEN (real Surelog) ACTUALLY DOES, measured cell by cell.
`ref+ec` = a ref_obj bound to a fresh loc-less enum_const (a REFUSAL);
`const`  = a folded constant;  `ts` = whether golden stamps an int_typespec.

================ 1. THE IMPORT SITE  (a3, a6, a7 — THE LAW'S MISSING FENCE)

The read is always the same: an unqualified package parameter in the CONDITION
of a `for` inside a gen-scope `always_comb` (plus a `repeat` COUNT twin).

  where the providing import is declared          golden   arm
  ----------------------------------------------  -------  -----------------
  MODULE BODY      `import p::*;`                  ref+ec   a3 (control), a7 gb_a
  MODULE HEADER    `module m import p::*; #(...)`  ref+ec   a7 gh_a
  MODULE BODY      `import p::P;`  (explicit)      ref+ec   a6 gz_a
  GENERATE BLOCK   `import p::*;`                  const+ts a3 gi_a
  GENERATE BLOCK   `import p::P;`  (explicit)      const+ts a3 gi_d
  MODULE **AND** GENERATE BLOCK, same package      const+ts a6 gx_a
  module imports p, GEN BLOCK imports q:
        the read of p's P                          ref+ec   a6 gy_a
        the read of q's Q                          const+ts a6 gy_a
  module header imports p, GEN BLOCK imports q:
        the read of p's P                          ref+ec   a7 gn_a
        the read of q's Q                          const+ts a7 gn_a
  inside the PROCESS's own begin block             const+ts a3 gi_b
  COMPILATION UNIT (`$unit`) only                  const+ts a3 gu_a
  QUALIFIED `p::P`, any of the above               const     a3 gi_c, gi_ee

  THE RULE: the INNERMOST PROVIDER decides.  Golden refuses exactly when NO
  scope between the read and the module body provides the name AND the module
  body itself does.  That is the predicate V-FIX v76 (a) implements.  It is
  also consistent with the implementer's own decode — a generate block IS its
  own DesignComponent, so an import ON it materialises the parameter INTO its
  `param_assigns` with `VpiImported()` set and the COMPONENT-level arm of
  CompileExpression.cpp:2915-2977 fires there too.

  As shipped, the patch refused in all SIX `const` rows above: a KIND flip
  (`constant` -> `ref_obj`) on the first field BaseClass::Compare tests, from a
  state that differed from golden only by the missing int_typespec.

================ 3. THE PROCEDURE KIND  (a5, a8 — A WHOLE CONTAINER THE LAW
                    DOES NOT COVER; both binaries are WRONG the same way, so
                    it is a residue, V-R1, not a regression)

  gen-scope process     position                      golden    ours (both bins)
  --------------------  ----------------------------  --------  ----------------
  always_comb           plain statement               const+ts  const+ts   OK
  always @(posedge clk) body statement                const+ts  const+ts   OK
  always (no event ctl) body statement                const+ts  const+ts   OK
  always_comb           case EXPRESSION `case (NB)`   const+ts  const (no ts)
  INITIAL               plain statement               ref+ec    const   WRONG
  INITIAL               `if` condition                ref+ec    const   WRONG
  INITIAL               one-statement `initial x = NB`ref+ec    const   WRONG
  INITIAL               forever body, plain           ref+ec    const   WRONG
  INITIAL               forever body, `@(posedge)`    ref+ec    const   WRONG
  INITIAL               `#5 x = x + NB;`              ref+ec    const   WRONG
  FINAL                 body statement                ref+ec    const   WRONG

  The implementer's comment "golden FOLDS in the `while`, `do…while`,
  `repeat`, `foreach` and `forever` bodies" names `forever` WITHOUT HAVING
  BUILT ONE — g1_gsfor76.sv contains no `forever` at all — and it is FALSE.
  The real discriminator is the PROCEDURE KIND: a gen-scope `initial` or
  `final` refuses EVERYWHERE in its body, an `always`-family process refuses
  only in the for statement and the loop controls.  7 cells on a8, 0 corpus.
