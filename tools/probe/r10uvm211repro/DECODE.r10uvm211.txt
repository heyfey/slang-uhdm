3. SURELOG — WHY GOLDEN LOOKS LIKE THAT
---------------------------------------

`CompileHelper::importPackage` (Surelog src/DesignCompile/CompileHelper.cpp,
the task_func loop at :300-330) deep-copies each imported subroutine into the
IMPORTING scope at COMPILE time:

    if (inPackage) {
      ElaboratorContext elaboratorContext(&s, false, true);
      task_func* clone = (task_func*)UHDM::clone_tree((any*)func, &elaboratorContext);
      sfuncs->push_back(clone);
    }

`clone_tree` is a DEEP copy, so every declaration in the cloned body gets its
own array typespec, its own element ref and its own struct copy — golden's
arity of 1, measured above.

`UhdmWriter::writeDataTypes` (src/DesignCompile/UhdmWriter.cpp:775-796) applies
the `p::t` prefix IN PLACE, while the HOME package's own `datatypeMap` walk
runs:

    if (parent->UhdmType() == uhdmpackage) {
      if (tps && (tps->VpiName().find("::") == std::string::npos)) {
        const std::string newName = StrCat(parent->VpiName(), "::", tps->VpiName());
        tps->VpiName(newName);
      }
    }

The clone was made BEFORE that walk, so nothing inside a clone body is ever the
object that got prefixed — at any depth and in any role, an array element's
struct member included.  The rule has not changed since § 16; only the link has.

The `object_name` filter three lines above the clone is why a NAMED import is
cloned too — and why arm E's residue stands on purpose (§ 194's committed fence
makes `pkgImportCloneTfs16` WILDCARD-ONLY).
