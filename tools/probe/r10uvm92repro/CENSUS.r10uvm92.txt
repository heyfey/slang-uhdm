=============================================================================
1. GOLDEN-vs-GOLDEN — THE DECODE AS AN ORACLE  (gvg92.sh)
=============================================================================
`ct92cen` LINKS THE REAL `UHDM::ExprEval::prettyPrint` and transcribes
`CompileHelper::decompileHelper`, applies the composition to every path element
of a golden database's OWN tree, and compares the result to the bracket text
that database's hier_path NAME actually carries.  EXPM=Y is a per-object proof.

  corpus       goldens   op-index hier_paths   EXPM_Y   EXPM_N   refuting goldens
  surelog       1523          10021            10036       0            0
  uhdm2rtlil    1458           1840             1844       0            0

11,880 cells over 2,981 golden databases, ZERO exceptions.
(EXPM counts CELLS, the hier_path column counts OBJECTS; a path can carry two.)

THREE CENSUS BUGS were found getting there, each of which PRINTED AS A
REFUTATION and none of which was one -- recorded because "the instrument was
wrong" is the reading a pass must not silently discard:
  * a component name matched INSIDE a longer one: `memory` in `i_memory_tb`
    (Scr1SvTests, a CMP_EQUAL row) and `data` in `data_o` (Ariane2024);
  * a SECOND-DIMENSION element carries NO VpiName at all
    (`rw.value[idx][i0 * 8+:8]`, BuildUVMPkg/Monitor/Opentitan/CoresSweRV);
  * a greedy scrape handed the FIRST element BOTH bracket groups.
The scraper now walks a CURSOR, requires BOTH component boundaries, and consumes
exactly the number of groups the element's own decompileHelper row emits.
